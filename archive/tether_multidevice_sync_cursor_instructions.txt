TETHER — MULTI-DEVICE PAIRING + REAL-TIME SYNC INTEGRATION BRIEF FOR CURSOR AI

Project context
- App name: Tether
- App type: aesthetic minimalistic web app formatted around mobile/iPhone dimensions, later convertible to iOS.
- Preferred stack: React frontend, Python backend where useful, CSS for aesthetics, Supabase is acceptable and should be used for convenience.
- Goal: allow two people’s apps/accounts/devices to be paired together and interact with one another in near real time.

Recommended approach
Use Supabase as the main sync layer:
1. Supabase Auth for user identity.
2. Supabase Postgres for persistent shared data.
3. Supabase Realtime channels for instant updates between paired users.
4. Supabase Presence for online/active state.
5. Optional Python FastAPI backend only for actions that should not be trusted to the client, such as validating pair codes, server-side cleanups, notification jobs, or future AI features.

Why this approach
- Supabase is already aligned with the current planned stack.
- It avoids needing to run a separate WebSocket server.
- It has a free tier suitable for an MVP and small student project.
- It supports auth, database, realtime events, and row-level security in one place.
- React can connect directly to Supabase using the official client.

Core product behaviour
- Every user has an account.
- A user can generate a temporary pairing code.
- Another user enters that code.
- Once accepted, a pair record is created.
- Both users subscribe to the same pair-specific realtime channel.
- Any shared interaction, such as mood update, moment upload, nudge, status, note, activity, or reaction, is saved to Supabase and reflected live on the partner’s device.

Important implementation principle
Use the database as the source of truth. Realtime should update the UI quickly, but important user actions must also be stored in Postgres so they survive refreshes, app restarts, and multi-device login.

Database schema
Create these core tables in Supabase.

1. profiles
Purpose: basic user profile linked to Supabase Auth.

SQL:
create table if not exists public.profiles (
  id uuid primary key references auth.users(id) on delete cascade,
  display_name text,
  avatar_url text,
  created_at timestamptz default now()
);

2. pair_codes
Purpose: temporary code generated by one user so another user can pair with them.

SQL:
create table if not exists public.pair_codes (
  id uuid primary key default gen_random_uuid(),
  creator_id uuid not null references public.profiles(id) on delete cascade,
  code text not null unique,
  expires_at timestamptz not null,
  used_at timestamptz,
  created_at timestamptz default now()
);

3. pairs
Purpose: permanent relationship between two paired users.

SQL:
create table if not exists public.pairs (
  id uuid primary key default gen_random_uuid(),
  user_a uuid not null references public.profiles(id) on delete cascade,
  user_b uuid not null references public.profiles(id) on delete cascade,
  status text not null default 'active',
  created_at timestamptz default now(),
  constraint different_users check (user_a <> user_b)
);

4. pair_events
Purpose: append-only realtime feed for shared interactions.

SQL:
create table if not exists public.pair_events (
  id uuid primary key default gen_random_uuid(),
  pair_id uuid not null references public.pairs(id) on delete cascade,
  sender_id uuid not null references public.profiles(id) on delete cascade,
  event_type text not null,
  payload jsonb not null default '{}'::jsonb,
  created_at timestamptz default now()
);

Example event_type values:
- mood_update
- nudge
- moment_created
- reaction_added
- status_update
- shared_note_created
- heartbeat

5. moments
Purpose: persistent shared photo/text moments.

SQL:
create table if not exists public.moments (
  id uuid primary key default gen_random_uuid(),
  pair_id uuid not null references public.pairs(id) on delete cascade,
  creator_id uuid not null references public.profiles(id) on delete cascade,
  caption text,
  image_url text,
  created_at timestamptz default now()
);

RLS policies
Use policies that ensure users can only access their own pair data.

profiles:
- Users can read their own profile.
- Users can update their own profile.

pairs:
- Users can select pairs where auth.uid() is user_a or user_b.
- Users can insert a pair only through a secure backend function or carefully validated RPC.

pair_events:
- Users can select events for pairs where they are user_a or user_b.
- Users can insert events only for pairs where they are user_a or user_b, and sender_id must equal auth.uid().

moments:
- Users can select moments for pairs where they are user_a or user_b.
- Users can insert moments only for pairs where they are user_a or user_b, and creator_id must equal auth.uid().

Suggested SQL policies:

create policy "Users can read their own profile"
on public.profiles for select
to authenticated
using (id = auth.uid());

create policy "Users can update their own profile"
on public.profiles for update
to authenticated
using (id = auth.uid())
with check (id = auth.uid());

create policy "Users can read own pairs"
on public.pairs for select
to authenticated
using (auth.uid() = user_a or auth.uid() = user_b);

create policy "Users can read own pair events"
on public.pair_events for select
to authenticated
using (
  exists (
    select 1 from public.pairs
    where pairs.id = pair_events.pair_id
    and (pairs.user_a = auth.uid() or pairs.user_b = auth.uid())
  )
);

create policy "Users can create events in own pair"
on public.pair_events for insert
to authenticated
with check (
  sender_id = auth.uid()
  and exists (
    select 1 from public.pairs
    where pairs.id = pair_events.pair_id
    and (pairs.user_a = auth.uid() or pairs.user_b = auth.uid())
  )
);

create policy "Users can read own moments"
on public.moments for select
to authenticated
using (
  exists (
    select 1 from public.pairs
    where pairs.id = moments.pair_id
    and (pairs.user_a = auth.uid() or pairs.user_b = auth.uid())
  )
);

create policy "Users can create own moments"
on public.moments for insert
to authenticated
with check (
  creator_id = auth.uid()
  and exists (
    select 1 from public.pairs
    where pairs.id = moments.pair_id
    and (pairs.user_a = auth.uid() or pairs.user_b = auth.uid())
  )
);

Pairing flow
Implement this UX:
1. User A taps “Pair with someone”.
2. App generates a short 6-character code and inserts it into pair_codes with expiry of 10 minutes.
3. User A shares the code manually.
4. User B enters the code.
5. App validates that the code exists, has not expired, has not been used, and was not created by User B.
6. App creates a row in pairs.
7. App marks pair_codes.used_at = now().
8. Both users are redirected to the shared Tether home screen.

Recommended: implement pairing code creation and redemption via Python backend or Supabase RPC so the operation is harder to abuse.

Python backend pairing route idea
Use FastAPI with the Supabase service role key for pair creation only.

Endpoints:
POST /pairing/create-code
- Auth required.
- Reads user id from JWT.
- Generates secure 6-character code.
- Inserts pair_codes row.
- Returns code and expires_at.

POST /pairing/redeem-code
- Auth required.
- Reads user id from JWT.
- Validates code.
- Creates pair row.
- Marks code as used.
- Returns pair_id.

Realtime sync hook
Create /frontend/src/features/sync/usePairRealtime.js.

Behaviour:
- Accept pairId and currentUserId.
- Subscribe to a Supabase realtime channel named `pair:${pairId}`.
- Listen for INSERT changes on pair_events where pair_id equals current pair.
- Update local UI state when new events arrive.
- Clean up subscription on unmount.

Example structure:

import { useEffect } from 'react';
import { supabase } from '../../lib/supabaseClient';

export function usePairRealtime(pairId, onEvent) {
  useEffect(() => {
    if (!pairId) return;

    const channel = supabase
      .channel(`pair:${pairId}`)
      .on(
        'postgres_changes',
        {
          event: 'INSERT',
          schema: 'public',
          table: 'pair_events',
          filter: `pair_id=eq.${pairId}`,
        },
        (payload) => {
          onEvent(payload.new);
        }
      )
      .subscribe();

    return () => {
      supabase.removeChannel(channel);
    };
  }, [pairId, onEvent]);
}

Sending synced events
Create /frontend/src/features/sync/syncEvents.js.

import { supabase } from '../../lib/supabaseClient';

export async function sendPairEvent({ pairId, senderId, eventType, payload }) {
  const { data, error } = await supabase
    .from('pair_events')
    .insert({
      pair_id: pairId,
      sender_id: senderId,
      event_type: eventType,
      payload,
    })
    .select()
    .single();

  if (error) throw error;
  return data;
}

Presence
Create /frontend/src/features/presence/usePresence.js.

Behaviour:
- Subscribe to channel `presence:${pairId}`.
- Track current user online state.
- Show partner as online/offline/active.

Example:

import { useEffect, useState } from 'react';
import { supabase } from '../../lib/supabaseClient';

export function usePresence(pairId, user) {
  const [presenceState, setPresenceState] = useState({});

  useEffect(() => {
    if (!pairId || !user) return;

    const channel = supabase.channel(`presence:${pairId}`, {
      config: { presence: { key: user.id } },
    });

    channel
      .on('presence', { event: 'sync' }, () => {
        setPresenceState(channel.presenceState());
      })
      .subscribe(async (status) => {
        if (status === 'SUBSCRIBED') {
          await channel.track({
            user_id: user.id,
            online_at: new Date().toISOString(),
          });
        }
      });

    return () => {
      supabase.removeChannel(channel);
    };
  }, [pairId, user]);

  return presenceState;
}

Conflict handling
- For append-only interactions like nudges, reactions, and moments, simply insert new pair_events.
- For single-current-state fields like “current mood”, either:
  a. store every update in pair_events and compute latest mood, or
  b. create a pair_state table with upsert logic.
- For MVP, prefer event log first because it is easier to debug and sync.

Optional pair_state table for latest state
Use this later if needed:

create table if not exists public.pair_state (
  pair_id uuid primary key references public.pairs(id) on delete cascade,
  state jsonb not null default '{}'::jsonb,
  updated_at timestamptz default now()
);

Security requirements
- Never allow users to read events from pairs they are not part of.
- Never allow sender_id to be different from auth.uid().
- Never expose service role key in frontend.
- Pair codes must expire quickly.
- Pair codes should be random and not predictable.
- Prevent pairing with self.
- Consider allowing only one active pair per user for MVP unless the product requires multiple pairs.
